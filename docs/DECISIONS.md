## ADR-001: Dataset = PneumoniaMNIST (MedMNIST v2), one CSV per site
Date 2026-10-13, central.
**Context**: PROJECT_PLAN.md §5 needs a public, login-free, health-related dataset that trains to a meaningful score on CPU in minutes and fits one CSV/Parquet file per site.
**Decision**: PneumoniaMNIST (Yang et al., MedMNIST v2, CC BY 4.0; source: Kermany et al. chest X-rays). File `pneumoniamnist.npz` from Zenodo record 10519652 (4.17 MB, md5 `28209eda62fecd6e6a2d98b1501bb15f`, sha256 `e1792d3f03751cb101e99f19a63b3c1941436c988665f47853417b05be250cd8`). 28x28 grayscale, binary (normal / pneumonia).
Official train split (4,708) → 6 IID partitions with `RandomState(2026).permutation` (frozen numpy stream): 785/785/785/785/784/784 for nvf-h1, nvf-h2, v6-h3, v6-h4, flw-h5, flw-h6. One CSV per site (`label,x0..x783`, integer pixels), sha256 of every site file pinned in `flhub_core.data.PARTITION_SHA256`. Test split (624, 62.5 % pneumonia) stays on the central VM for global evaluation; the val split is unused.
Model: CNN conv(1→8)→pool→conv(8→16)→pool→fc(784→64)→fc(64→2), ReLU, no normalization layers; 51,618 parameters, 206 KB float32.
**Consequences**: tiny payloads and ~1 s per local round per site on one CPU thread; binary task gives accuracy + AUC. MedMNIST's test split is shifted against train (published ResNet-18 test acc ≈ 85 %), so expect ~85 % rather than the ~95 % validation accuracy. The CDC diabetes table was rejected because its accuracy barely beats the 86 % majority baseline.

## ADR-002: Version pins (deploy/versions.env)
Date 2026-10-13, central.
**Context**: the plan asks for latest stable versions, Python 3.11 and vantage6 4.15.x.
**Decision**: Python 3.11.17 (uv), torch 2.14.1+cpu, numpy 2.4.4, safetensors 0.8.0, NVFlare 2.9.0, vantage6 4.15.2, flwr 1.39.0, wandb 0.30.0, registry:2. numpy 2.5 requires Python ≥ 3.12, so 2.4.4 is the newest usable; vantage6 5.x (latest 5.0.3, Python ≥ 3.13, Kubernetes) is excluded by the plan.

## ADR-003: Determinism without hospital-side configuration
Date 2026-10-13, central.
**Context**: §5 seeds the data order with (seed, round, partition_index). A real hospital has no "partition index", and passing one would be hub-specific client config.
**Decision**: the data order is seeded with sha256(`seed`, `round`, data fingerprint), where the fingerprint is the sha256 of the site's canonical uint8 pixels + int64 labels. Same data => same order, with zero configuration; the reference simulation reproduces it by loading the same files. Training uses 1 CPU thread, `use_deterministic_algorithms(True)`, a fresh SGD (foreach=False) per call, no dropout. `python -m flhub_core.selfcheck` prints the sha256 of one local round; all VMs and the vantage6 image must print the same value.
**Consequences**: bit-exact cross-framework FedAvg is possible if all CPUs take the same kernel paths (central VM: AMD EPYC-Rome, AVX2). If selfcheck differs across VMs, the fallback is pinning `ATEN_CPU_CAPABILITY`/`MKL_CBWR`/`ONEDNN_MAX_CPU_ISA` (new ADR).

## ADR-005: vantage6 4.15.2 CLI workarounds on Python 3.11
Date 2026-10-13, vantage6.
**Context**: vantage6 4.15.2 declares Python ≥ 3.10, but its CLI f-strings `(str, Enum)` members; Python 3.11 formats them as `Class.MEMBER`. Effects: `v6 server import` passes its DB location as env var `ServerGlobals.DB_URI_ENV_VAR` instead of `VANTAGE6_DB_URI`, so the import writes into a throw-away container DB; the server container is named `vantage6-<name>-user-ServerType.V6SERVER`, so `v6 server stop -n` cannot find it. Also, server/node containers (root) write the shared log dir, so later CLI calls fail with "Can't write to log dir", and a fresh server creates superuser `root`/`root` unless a user `root` exists.
**Decision**: install.sh runs the server image's own `vserver-local import` with `VANTAGE6_DB_URI` set; the server is started with `v6 server start -c <config> --user` (no CLI file logging) and stopped by Docker label; nodes are stopped with `docker stop vantage6-<site>-user`; the entities file imports `root` with a generated password. Server and node configs are written from templates (`v6 server new`/`v6 node new` are interactive only).
**Consequences**: no patched vantage6 code; standard images and config formats. Revisit if the CLI is upgraded.

## ADR-006: NVFlare relay = one long-running job, kept alive by the adapter
Date 2026-10-13, nvflare.
**Context**: PROJECT_PLAN.md §3 puts a ModelController relay inside the NVFlare server, but does not say how its job lives, how hub sites map to NVFlare clients over time, or how "online" is decided. Observed in NVFlare 2.9.0: (a) the server keeps a stopped client "connected" (`get_system_info`, `get_client_disconnect_time`) for minutes; (b) a restarted client does not rejoin a job that is already running; (c) `ScriptRunner` with an absolute script path makes clients run that local path instead of the shipped `custom/` copy.
**Decision**: one job `flhub-relay` (FedJob, min_clients = 2, deploy `@ALL`): server workflow `adapters.nvflare.relay_controller.HubRelayController` from the installed package, clients `ScriptRunner("client.py", framework=NUMPY)` in-process (relative path, so the job ships `custom/client.py`). The adapter (`adapters/nvflare/service.py`) submits it through the FLARE API with the operator's admin kit, adopts a running one, and restarts it gracefully (relay shutdown, then resubmit) when a connected site has been outside the job for 15 s and no round is in flight. A site is online only if the relay reports it as a live job client AND the server's `get_client_job_status()` probe shows the client running that job (a dead client answers `no_reply`). A round on an offline site fails at once instead of waiting for the deadline.
**Consequences**: hospital restarts and server restarts heal without operator action (verified: offline within 5 s; both online again ~50 s after a client restart; ~20 s after a server restart). A job restart briefly takes both NVFlare sites offline. Training code reaches hospitals only as job custom code (BYOC, allowed for the project_admin submitter; BYOC jobs bypass the 2.9 client class allow-list).

## ADR-007: Flower 1.39 server side: one HTTP API port, persistent SuperLink, supervised SuperNodes
Date 2026-10-13, flower.
**Context**: Flower 1.39 dropped the ServerAppIo gRPC API (plan port 9091): `flwr run` and the ServerApp both use one SuperLink HTTP API (`--host/--port`), and `--clientappio-api-address` became a per-SuperNode `--port`. The SuperLink installs FAB dependencies at runtime by default. A SuperNode exits (self-SIGINT on `UNAUTHENTICATED`) when a restarted in-memory SuperLink no longer knows its node id, so a central redeploy would silently take the hospitals offline. SuperNode ids are random per start; the ServerApp cannot see `--node-config`.
**Decision**: SuperLink `--insecure --fleet-api-address 0.0.0.0:9092 --host 127.0.0.1 --port 9093 --database ~/flhub-runtime/flower/superlink.db --disable-runtime-dependency-installation` (9093 = local HTTP API, 9091 unused; deps preinstalled). Hospitals run the standard `flower-supernode` under `deploy/flower-vm/supernode.sh`, which restarts it if it exits (like systemd `Restart=always`); runtime ports 9094/9095 on the flower VM only, one `FLWR_HOME` per node. The relay ServerApp maps node id -> site with a standard QUERY message answered by the ClientApp's `@app.query()` (newest node wins per site) and reports sites to the adapter; the adapter keeps one relay run alive via `flwr run`.
**Consequences**: SuperNodes keep their ids across SuperLink restarts and recover by themselves if its state is lost; no hub code on hospitals beyond `flhub_core` + the node config (`site-id`, `data-path`). Flower without TLS/SuperNode auth stays a documented test-network limitation (stretch goal).

## ADR-008: flhub/0.2 — per-site progress, partial collect, per-site cancel
Date 2026-10-13, central (stage 2).
**Context**: stage 2 needs partial participation (`min_sites`, stragglers, dropouts; PLAN.md stage 2 §4.3–§4.4), 12 registered sites of which only some are online, and payloads up to 1 GB. flhub/0.1 only knows whole tasks, all-or-nothing collect, a 64 MB cap and "ready = all sites online".
**Decision**: flhub/0.2 (PROTOCOL.md §7) adds optional fields only: `tasks/get` per-site states, `collect {partial: true}`, `cancel {sites}`, discover `protocols` + capability flags, `max_payload_mb` ≥ 1024, per-run readiness. A 0.2 adapter serves 0.1 callers unchanged (it echoes the request's version, also in envelopes); the orchestrator negotiates with `discover`. `adapters/common` implements it once: `Task` keeps a state and envelope per site, `BaseAdapter.report_site()` / `report_site_error()` hand over one site at a time, `-32015` is per site, the deadline fails only the sites still active, and `RelayAdapter` gets `/relay/site_result`, `/relay/site_error` and `/relay/job`. Hub core and `RpcServer` accept 2 GiB bodies and stream blobs; `DELETE /blobs` and `/admin/gc` allow blob GC.
**Consequences**: 0.1-style adapters keep working on the new base (all results at the end), but only adapters that report per site and stop cancelled sites promptly make `min_sites` effective; that part is framework work (NVFlare relay, Flower relay, vantage6 runs). Conformance v2 tests it: subset dispatch, partial collect + per-site cancel + immediate next dispatch, offline site not blocking, restart between rounds, payload-64 echo.

## ADR-009: Stage-2 dataset OrganAMNIST, partitions and data variants
Date 2026-10-13, central (stage 2).
**Context**: stage 2 needs a multi-class dataset for label skew (PLAN.md stage 2 §4.2), deterministic partitions for the pids of EXPERIMENTS.md, and a way to switch a site's data per run without hospital code changes or a manual step per run.
**Decision**: D = OrganAMNIST 28 px (MedMNIST v2, CC BY 4.0; Zenodo record 10519652, `organamnist.npz` 38,247,708 B, md5 `68e3f8846a6bd62f0c9bf841c0d9eacc` = MedMNIST's, sha256 `7c8c8b0753e2c0d7f70928817eac02be7cbb09f6beff4346e9d0ea79ecb598bd`): 11 abdominal CT organ classes, train 34,561 / val 6,491 / test 17,778 (BloodMNIST is smaller, PathMNIST too slow on CPU). Partitions (`flhub_core.partition`, partition_seed 2026, numpy's frozen legacy RandomState seeded from sha256(seed, purpose)): iid, iid12 and qty are stratified (an evenly interleaved site schedule over the class-sorted, shuffled split); dir<α> follows the plan (sites in order, round(q_k n_k) per class, shortfall of an exhausted class redistributed in proportion to q_k); fwcorr draws per-class framework shares from Dirichlet(0.3·1₃) and halves them IID; mix reuses dir0.3's q_k with the qty sizes. Manifests (n, label histogram, CSV sha256, data fingerprint per site) are committed in `configs/stage2/partitions/`; `pneumoniamnist-iid` is the stage-1 split (same sha256 as stage 1).
A data variant is `<dataset>-<pid>` in file `<variant>-<site>.csv`, chosen by `train_config["data_variant"]`. `load_site(path)` returns a lazy `SiteSource`: next to a `<site>.csv` path the variant is `<variant>-<site>.csv`; in a directory the one `<variant>-*.csv`; no variant = the stage-1 data. DataFrames are used as given (vantage6 labelled databases, picked by the dispatch hint `data_variant`). Every envelope reports `data_fp` (first 32 bits of the data fingerprint), which the hub checks against the manifest.
**Consequences**: hospitals keep their stage-1 data path; provisioning is data only (`python -m flhub_core.data materialize --variants all --sites <sites> --manifests configs/stage2/partitions`, about 110-150 MB per base site). With equal site sizes and a small α, classes run out, so the last sites take the leftovers and dir0.1 is only slightly more skewed than dir0.3; the realized histograms are in the manifests and `docs/report/stage2/figures/partitions.png`.

## ADR-010: flhub_core 0.2 model zoo, training options and selfcheck v2
Date 2026-10-13, central (stage 2).
**Context**: PLAN.md stage 2 §4.2 asks for larger models, a synthetic payload model, FedProx, optimizer options and timing metrics, while the stage-1 config must stay bit-exact.
**Decision**: models (no BatchNorm, float32 parameters only): `cnn-small` (stage-1 Net; 52,203 parameters with 11 classes), `cnn-medium` (2×conv32, 2×conv64, fc 3136→512→C; 1,676,779), `resnet18-gn` (CIFAR stem, GroupNorm(32); 11,173,323, 42.6 MiB), `payload-<MB>` (4 MiB float32 tensors, PCG64 normal×0.01 init; "training" = w + 1e-3·c(seed, round, data fingerprint, tensor), no torch). Optional flat train_config keys `model`, `data_variant`, `prox_mu` (adds μ(w−x) to the gradient after backward; μ = 0 skips it), `weight_decay` (SGD); `TrainConfig.from_dict` keeps them. Metrics add `train_time_s`, `data_load_s`, `peak_rss_mb`, `data_fp`. `code_version()` hashes every .py of the package (same value as before for a flat package). Selfcheck v2 needs no files: one hash per model on synthetic 11-class data plus a prox/weight-decay/momentum case and a digest line; `--v1` still prints the stage-1 hash `7c80a5a3…`. Client-side imports stay numpy, torch, safetensors.
**Consequences**: absent keys reproduce stage 1 (selfcheck v1 unchanged). Every site must run byte-identical flhub_core 0.2 (content-hash code_version) and match the selfcheck v2 digest before S2 ends.

## ADR-011: NVFlare adapter flhub/0.2 — one task per site; a site fails alone
Date 2026-10-13, nvflare.
**Context**: flhub/0.2 (ADR-008) needs per-site results, per-site failure and per-site cancel. In NVFlare 2.9.0 `send_model_and_wait` returns all replies at once and, with `ignore_result_error`, drops error replies silently; a broadcast task can only be cancelled as a whole and deep-copies its data once per task (`wf_comm_server.py:308-314`); the server declares a killed client dead only after `dead_client_grace` (60 s) plus a 30 s lead time. With `min_clients` = all base sites, the relay job could not start while one base site was down.
**Decision**: the relay sends one NVFlare task per site (`_prepare_task` + `Controller.send(targets=[site], SendOrder.ANY)`: same FULL `FLModel`, task name and client code as before, no deep copy). Each reply goes to the adapter as soon as it arrives (`/relay/site_result`), an error reply (return code not OK) at once as `/relay/site_error`; every second the relay polls `/relay/job` and cancels the NVFlare task of every site the hub no longer waits for. The adapter fails offline sites at dispatch, and sites that are offline for 30 s during a round (relay view + FLARE API probe; an unknown probe result never fails a site). The relay job has `min_clients = 1`; the keeper submits it once every base site is connected, or 30 s after the first one connected (one job start after a server restart). Extra sites (E5) are served but never block; `status.sh` judges the base sites.
**Consequences**: partial collect, per-site cancel and `min_sites` work with NVFlare (island conformance v2: 11 passed, max abs diff 0.0; `docs/report/stage2/evidence/nvflare/`). NVFlare has no per-task abort towards a client: a cancelled site finishes its local training, its late result is dropped, and its next task waits behind it (relevant for E6b stragglers).

## ADR-013: vantage6 adapter on flhub/0.2: one vantage6 task per site and round
Date 2026-10-13, vantage6.
**Context**: flhub/0.2 needs per-site progress, partial collect and per-site cancel (ADR-008). In vantage6 4.15.2 a multi-organisation task turns `failed` as soon as one run fails, `/kill/task` then refuses ("already finished") to stop the other runs, `/kill/node/tasks` kills every container of a node without updating run states, and `GET /run` always returns each run's full input (base64(json(input)) ~1.78x the model), so per-run polling costs a model transfer per site and poll.
**Decision**: `adapters/vantage6` creates one vantage6 task per site (method `train`, `organizations=[org]`, name `flhub-r<round>`). Per site it polls the cheap `task/<id>/status`, fetches that task's single result as soon as it completes and reports it (`report_site`), reports a failed run with its log (`report_site_error`), and cancels a site with `task.kill` (marks pending runs `killed` too). Inputs and results move on per-site sessions, status polls and kills on a control session that gives up after 2 connection errors (the client otherwise retries forever), so a vantage6 server outage only delays a round (E6e) and `discover` answers `unknown` meanwhile. For models >= 16 MB (`V6_PURGE_MIN_MB`) the round's vantage6 tasks are deleted once the round is settled, which keeps the server DB at one round (resnet18-gn, payload runs). Missing organisations (E5 sites before `add_sites.sh`) are reported offline instead of failing the login.
**Consequences**: still standard vantage6 usage (tasks per organisation through the user client); hospitals see the same `train` tasks as before. Island: conformance v2 11/11, max abs diff 0.0; a mid-round server restart with 30 s downtime completes the round without a retry.

## ADR-014: vantage6 data variants = one labelled node database per variant
Date 2026-10-13, vantage6.
**Context**: stage 2 runs several data variants `<dataset>-<pid>` per site without code changes per run (PLAN.md §4.2). A vantage6 algorithm receives its data from the node as a DataFrame of the database the task names; `flhub_core.data.load_site(DataFrame)` gives concrete data and `train()` uses it as given (ADR-009). Node database labels must be Python identifiers (`v6 node start` checks `label.isidentifier()`).
**Decision**: each node config lists one CSV database per stage-2 variant, label `db_label(variant)` = the variant with every non `[A-Za-z0-9_]` character replaced by `_` (`organamnist-dir0.3` -> `organamnist_dir0_3`), plus the stage-1 `default`. The adapter takes the variant from the flhub/0.2 dispatch hint `data_variant` (train_config stays opaque) and creates the task with `databases=[{"label": db_label(variant)}]`; no hint -> `default`. The hub checks every site's data through the `data_fp` metric.
**Consequences**: hospital side = data provisioning plus a node config change and one node restart (ledger); the algorithm code is unchanged. A missing label makes the node fail that run with the vantage6 error text.

## ADR-015: vantage6 E6 fault injection and straggler mechanisms
Date 2026-10-13, vantage6.
**Context**: E6 needs a kill or restart at a given hub round and one throttled site per framework. vantage6 4.15.2 nodes start algorithm containers (`vantage6-<node>-run-<run_id>`, labels `vantage6-type=algorithm`, `node=<node>`) without cpu limits and have no config knob for them; the node log streams the algorithm output live.
**Decision**: `deploy/vantage6-vm/inject.sh` triggers on the node log line the algorithm prints when training starts (`[Task <run_id>]: info > site=<site> ... round=<N>`), waits S seconds and then SIGKILLs the algorithm container (`kill`), SIGKILLs the node container (`kill-node`, the watchdog cron restarts it) or restarts the node (`restart`); one-shot, logged with UTC times. `deploy/vantage6-vm/straggler.sh` watches that node's algorithm containers and applies `docker update --cpus <cpu%/100>` to each within 0.2 s of its start (before torch is imported).
**Consequences**: no change to nodes or algorithm. Island: `kill` -> run `crashed`, task failed 2.7 s later, node stays up; `restart` -> the node re-runs the open run after reconnecting and the round completes without a retry (19.6 s vs 8 s); straggler 10 % -> 41 s vs 8 s per round.

## ADR-016: Flower rollout channel = flhub_core inside the FAB; relay liveness beat
Date 2026-10-13, flower.
**Context**: PLAN §4.5 prefers each framework's own code-distribution channel with zero hospital steps. Flower 1.39 ships one FAB per run (zip of the app dir's `*.py|toml|md|yaml|yml|json|jsonl`, ≤ 10 MiB; `test_*.py`, `lib/`, `build/`, `__pycache__` and symlinks are skipped). Each message runs a fresh `flwr-clientapp` that unpacks the run's FAB into `$FLWR_HOME/apps/<publisher>.<name>.<version>.<hash8>` and calls `sys.path.insert(0, app_dir)` before importing the ClientApp (`supercore/object_ref.py`); connected SuperNodes fetch a new FAB by hash without a restart. Hospital venvs keep `flhub_core` 0.1.0 preinstalled (fixed copy since S1). A SuperLink restart kills the relay ServerApp (parent-pid monitors) and nothing relaunches it; the stage-1 adapter noticed only after 45 s and the round in flight failed at its deadline.
**Decision**: at start-up the Flower adapter stages `clients/flower` plus the hub's `flhub_core` package into `~/flhub-runtime/flower/fab-src` and submits that dir with `flwr run`; its content id goes to the relay as run config `fab-id`. The relay posts `/relay/beat` every 5 s from its own thread (fab id, run id, `flhub_core` code_version, current job). The adapter treats 20 s without poll, progress or beat as a lost relay: rounds that relay had taken fail at once, and a new relay run is submitted (retry every 10 s while `flwr run` fails, 60 s settle time after a submit). A relay that reports another fab id is asked to shut down and replaced. Runtime dependency installation stays off on SuperLink and SuperNodes.
**Consequences**: rolling out `flhub_core` 0.2 = restarting the adapter on the new SHA; hospitals need no step and no restart. Verified on the flower island: SuperNodes running a venv with `flhub_core` 0.1.0 reported the FAB copy's marker version `0.1.99+29638ceb7307`; a SuperLink SIGKILL mid-round failed that round after 25 s, the retry completed 16 s later (stage 1: deadline). `flhub_core` must stay within the FAB rules (no data files, no `test_*.py`, client deps torch/numpy/safetensors only; agreed with central on the bus, #113). Rollback = restart the adapter on the old SHA.
## ADR-012: NVFlare E6 tools — log-triggered injections, CPU-quota straggler without restart
Date 2026-10-13, nvflare.
**Context**: E6 needs injections at "round N + S seconds" and a CPU-throttled straggler on the NVFlare VM. The hospital client prints only the end of a round (`[flhub] <site>: round N`); NVFlare logs the task receipt without the hub round. Restarting a client takes it out of the running relay job, and NVFlare 2.9.0 fails the whole job when a client's job process exits with an error (`fed_server.py:944-951`, no knob) or when a restarted client reports the job missing.
**Decision**: `deploy/nvflare-vm/inject.sh arm <site> kill|kill-job|restart --round N --after S` starts a one-shot stdlib watcher (`inject_watch.py`, system python3) that follows the site's job logs: round N starts at the first "got task assignment" after `[flhub] <site>: round N-1` (exact when the site takes part in every round, as in E6a/E6e). `kill` SIGKILLs the client and its job processes (hospital crash; the kit daemon restarts the client, the cron watchdog covers the daemon), `kill-job` only the training process, `restart` uses the kit's `restart.fl`. The watcher announces `E6 inject …` on the bus right before acting and records the client-side recovery. `straggler.sh on <site> <cpu%>` adopts the running client and job processes into a transient system scope with `CPUQuota` (systemd `StartTransientUnit` with PIDs), so the site stays in its relay job; `off` lifts the quota.
**Consequences**: verified on the island (`docs/report/stage2/evidence/nvflare/e6-tools-island.md`): kill → only the killed site fails (35 s), client back after 4 s, in a new relay job after ~62 s; kill-job → NVFlare ends the relay job for both sites at once; straggler 10 % slows that site ~3-4x on short rounds, no false offline. With one relay job for both NVFlare sites, any NVFlare site failure briefly takes the other NVFlare site out of the job as well (a job restart, ~15-30 s).
